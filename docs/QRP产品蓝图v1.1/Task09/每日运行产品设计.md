---

## 0. 设计结论

Task09 的工作边界冻结为：

```text
Complete the graph
        ↓
Deploy the graph
        ↓
Close the graph
```

不是：

```text
再写一个 run_system_b_daily()
→ 手工 run_a()
→ run_b()
→ run_c()
→ 再实现一遍 dependency / retry / status / timeout
```

2026-09-09 生产调研已经确认：

- QRP 日常生产的单一 authority 已是系统级 `qrp-atlas-jobs.service`；
- 29 个生产 job 全部由 QRP Job Runtime 调度，QRP 范围内 Hermes authority 已为 0；
- 现有 runtime 已具备 scheduler、dependency plan、lease、heartbeat、timeout、retry、runtime store 和 result log；
- 当前 System B 真实生产链已稳定运行到 `readiness → state → episode → HEIGHT/CAPACITY/RECOGNITION pools`；
- 真正缺口是后半链：若干已存在但未部署的事实/rank Contract，以及 formal strategy → final target → closeout 的生产边界；
- 生产 live manifest 与 repo manifest 已漂移，当前实际生效的 `qrp-atlas-jobs.service` unit 也未纳入 Git。

因此 Task09 首要目标不是扩充运行基础设施，而是**把已有能力组合成一个正式的每日 System B 产品**。

## 1. 目标与非目标

### 1.1 目标

Task09 必须完成：

1. 固定生产编排 Git SSOT，使实际生产 manifest / service definition 可版本化、可审计、可复现；
2. 对 System B Daily 所需 PipelineContract 做一次完整 Contract Graph Audit；
3. 为确属 System B Daily 必需、已经 formalized 但尚未部署的 Contract 增加 Production Job instance；
4. 建立一个正式的 `system_b_strategy_daily` 生产边界，复用 Task05/06/07 已有 strategy 语义生成每日正式决定与完整目标组合；
5. 建立一个薄的 `system_b_daily_closeout` 终点，确认每日产品完成并保存必要 provenance / upstream run reference；
6. 复用现有 Job Runtime 完成失败阻断、重试、重启恢复、同日重放与连续 daily run；
7. 使相同 trade date、输入快照、规则、参数和策略版本能够确定性重放到相同正式 target。

### 1.2 非目标

Task09 明确不做：

- 新 Scheduler；
- 新 Job Runner；
- 新 DAG / workflow engine；
- 新的 `SYSTEM_B_DAILY = [stage...]` 第二套声明体系；
- 在一个 Python 函数里硬编码整条 daily 调用顺序；
- 把 authorization / score / decision / portfolio resolver 分别包装成独立生产 Job；
- 为了“声明式”再造 Airflow 类通用平台；
- execution / broker / OMS / order plan / 实盘权限；
- 把所有 repo-only Pipeline 一律塞入 System B Daily；
- 顺带治理所有历史生产 defect、legacy shell 或非 System B pipeline。

> **硬 Scope Rule**：Task09 只处理“形成并稳定生产每日 System B 正式 target”所必须的图节点、部署实例和产品完成状态。

## 2. 现有编排模型继续作为唯一模型

### 2.1 业务能力层：`PipelineContract`

业务依赖、输入输出、目标日期、资源锁、幂等、事务、freshness、timeout/retry 等继续只由 formal PipelineContract 表达。

Dependency 的 SSOT 仍是：

```text
PipelineContract.dependencies
```

不得在 Task09 再维护第二份 stage dependency 表。

### 2.2 部署实例层：`ProductionJobDefinition`

Production Job 继续只负责：

```text
job_id
pipeline_id
enabled
schedule
timezone
fixed parameters
name / description
```

manifest 不增加业务 dependency 字段。

Contract dependency 继续由现有 resolver 在 runtime 中解析为唯一 job instance dependency；缺失实例、多实例歧义、依赖环必须 fail-closed。

### 2.3 Runtime 层

继续复用：

```text
JobScheduler
JobRunner
JobRuntimeStore
ExecutionControl
ResultLog
```

Task09 不复制上述能力。

## 3. Stage 是产品视图，不等于 Job

路线图中的：

```text
readiness
market
theme
role
asset_state
eligibility
strategy
target
closeout
```

是**产品解释层的阶段视图**，不是“一阶段必须对应一个新 Job”的指令。

冻结规则：

- 已有 formal Contract 可以直接承担一个或多个逻辑 stage；
- 一个逻辑 stage 可由多个已有 Contract 共同形成；
- strategy 内部的 authorization / score / comparison / decision / target resolution 保持 strategy 封装；
- 只有具备独立生产生命周期、独立 freshness / idempotency / persistence 边界的能力，才应成为 PipelineContract。

因此禁止为了让 stage 名字“对齐”而机械拆 Job。

## 5. 冻结设计决策

### D01 — 不新增第二套 orchestration

`PipelineContract + ProductionJobDefinition + Job Runtime` 是 v1.1 唯一正式生产编排体系。

### D02 — Git 成为 deployment SSOT

生产运行所使用的 job manifest 与 `qrp-atlas-jobs.service` 定义必须纳入 Git。

运行机 `/home/claire/apps/...` 中的 manifest 视为**部署副本**，不得继续作为 repo 外独立权威。

Secrets / token / machine secret value 不进入 Git；service/env 只引用受控配置路径。

### D03 — Strategy 内部语义保持封装

以下不拆成独立 Pipeline Job：

```text
authorization
score
comparison
entry/exit decision
portfolio constraint resolution
```

它们继续作为 formal strategy 的内部业务语义和可测试组件。

理由：它们共享一次策略决定生命周期，并不存在必须独立调度的生产价值；拆开只会重新制造 orchestration glue。

### D04 — 新增一个正式 Strategy Daily 生产边界

Task09 引入：

```text
pipeline_id = system_b_strategy_daily
```

它只做 production adapter：

1. 读取已经完成且通过 freshness 的正式上游事实；
2. 解析正式规则 / 参数 / strategy version；
3. 运行现有 System B formal strategy；
4. fail-closed 处理 authorization 缺失、输入缺失、版本不一致；
5. 产出并持久化/记录当日正式 strategy result 与完整 target；
6. 保存足够 provenance 供重放和审计。

它不得复制 `system_b_authorization.py`、`system_b_decision.py`、`system_b_portfolio.py` 的业务规则。

### D05 — 新增一个薄 Closeout 终点

Task09 引入：

```text
pipeline_id = system_b_daily_closeout
```

它依赖 `system_b_strategy_daily`，只负责确认每日产品已经完整形成。

Closeout 不重新计算任何市场、rank、strategy 或 target。

至少检查/记录：

```text
trade_date
production run identity
rule version set
parameter set
strategy code / version
required upstream run references
final target identity / digest
completion status
completed_at
```

### D06 — Fail-Closed 保持到底

任何正式依赖：

- 未部署；
- 当日未成功；
- freshness 不满足；
- 版本不匹配；
- authorization unavailable；
- target 无法确定；

都不得由 Task09 静默补默认值继续运行。

结果应是明确 BLOCK / FAILED，而不是生成“尽量可用”的 target。

### D07 — Schedule 不是依赖语义

Cron 只决定 job 何时成为 due；真正的先后关系继续来自 Contract dependencies。

不得靠“19:10 比 19:00 晚，所以应该没问题”代替依赖边。

### D08 — 非 System B defect 不自动阻塞 Task09

调研发现 `etf-daily-close` 0/25 成功、`etf-adj-factor-close` 持续 BLOCK，这是独立 production defect。

除非最终 System B Contract Graph 明确依赖 ETF 链，否则该 defect 单独治理，不扩大 Task09 scope。

### 6.1 Phase 1 必须冻结的事实图

Task09 实现前先通过 Graph Audit 得到唯一正式图：

```text
已有 daily market / state / episode / pools
                │
                ├── required theme / market / role facts
                │
                ├── required popularity producers
                │
                ├── asset rank
                │

                system_b_strategy_daily

                system_b_daily_closeout

“required” 必须由 System B 正式 strategy 的输入契约反推，不能由当前 repo 有哪些模块反推。

### 6.2 禁止形成的图

theme_job
role_job
authorization_job
score_job
decision_job

```

## 7. 实施阶段

### Phase 0 — Production Orchestration SSOT Governance

先固定生产基线，不改业务语义：

1. 将当前真实 29-job live manifest 收回 repo；
2. 将实际生效的 `qrp-atlas-jobs.service` 以可部署、无 secret 的形式纳入 `deploy/`；
3. 明确：Git version = deployment SSOT，runtime apps path = deployed copy；
4. 加最小校验，确保部署前 manifest 可通过现有 production-job validation；
5. 不在此阶段顺便改 schedule、业务 dependency 或修 pipeline defect。

Phase 0 完成后，生产编排基线才具备版本审计能力。

### Phase 1 — Contract Graph Audit

对 System B 每个正式输入逐项回答：

```text
需要什么事实？
哪个 Contract 是 owner？
是否已经 formalized？
是否已有 production instance？
dependency 是否唯一可解析？
目标日期 / freshness 是否一致？
是否属于 daily product 必需链？
```

输出唯一目标 DAG，并冻结进入 Task09 implementation 的节点清单。

### Phase 2 — Deploy Required Existing Contracts

只为 Phase 1 判定为必需的已有 Contract 增加 Production Job instance。

重点解决当前已知的 dangling dependency，例如若 asset/theme rank 被正式 Daily Product 需要，则 `dc_hot_ingest` / `ths_hot_ingest` 必须有唯一 production instance，不能让 dependency graph 在结构上不可满足。

### Phase 3 — `system_b_strategy_daily`

增加最薄 production adapter：

```text
formal upstream facts
        ↓
existing strategy registry / validation
        ↓
System B authorization + decision + portfolio semantics
        ↓
complete StrategyPortfolioTarget
```

要求：

- 不复制业务规则；
- 使用 formal strategy registration / validation；
- runtime context precedence 与 Task07-C 保持一致；
- authorization 缺失继续 fail-closed；
- 同日重跑可确定性重现；
- 输出完整 target，不输出零散信号作为正式产品。

### Phase 4 — `system_b_daily_closeout`

建立 terminal Contract。

只有全部 required upstream + strategy target 成功，closeout 才能 SUCCESS。

Closeout 的存在用于回答：

> “某个交易日的 System B Daily Product 是否完整、使用了什么版本和输入、最终 target 是什么？”

### Phase 5 — Production Mount & Continuous Daily Run

复用现有 `qrp-atlas-jobs.service`：

```text
现有 scheduler
    ↓
现有 dependency runtime
    ↓
新增/补齐的 System B production jobs
    ↓
system_b_strategy_daily
    ↓
system_b_daily_closeout
```

不增加新的 systemd timer 或 `system-b-daily.service` 第二 authority。

连续 daily run 本身是验收，不是新能力建设。

## 8. Retry / Failure / Replay 语义

### 8.1 Dependency failure

上游失败时，下游保持 BLOCKED；不得通过手工绕过 dependency 生成正式 target。

### 8.2 Retry

沿用 Job Runtime 现有 retry 机制：

- 原失败 evidence 保留；
- retry 创建新 attempt；
- 同一 trade date 的业务写入必须遵守各 Contract 的既有幂等语义；
- closeout 只引用最终有效完成链。

### 8.3 Restart recovery

不得新增 System B 私有恢复逻辑；继续依赖 runtime store / lease / stale recovery。

### 8.4 Deterministic replay

相同：

```text
trade_date
input snapshot
rule version
parameter set
strategy version
```

必须得到可解释且一致的 formal strategy result / target。

Task08 historical replay 与 Task09 daily production 应共享 strategy / target 业务语义，而不是维护两套规则。

## 9. 测试与验收

### 9.1 Contract Graph

必须证明：

- 所有 required dependency 都存在 production instance；
- 无 dependency ambiguity；
- 无环；
- `plan` 输出与设计图一致；
- 不依赖 cron 时间差隐式表达业务顺序。

### 9.2 Strategy Daily

至少覆盖：

- 正常授权 + 正常 target；
- authorization unavailable → fail-closed；
- authorization denied → 不产生 NEW/ADD；
- upstream rank/fact 缺失；
- 同日 EXIT / ENTER 约束；
- target gross / distinct / per-asset 约束；
- 同 snapshot 重跑 target 一致；
- 不修改历史已完成日期的业务身份。

### 9.3 Closeout

至少覆盖：

- 全链成功 → closeout SUCCESS；
- 任一 required upstream 非 SUCCESS → 不得成功 closeout；
- strategy 没有正式 target → 不得成功 closeout；
- retry 后引用正确最终 run；
- 重复执行不会产生多个互相矛盾的正式 daily product。

### 9.4 Production acceptance

沿用 v1.1 Gate：

```text
Gate 1  docs / contracts
Gate 2  unit + integration
Gate 3  PIT historical replay
Gate 4  strategy / target deterministic replay
Gate 5  existing production runtime continuous daily run
Gate 6  release/v1.1-acceptance
```

Gate 5 不建立专用连续运行框架；就是正式生产 DAG 连续运行并观察结果。

## 12. 最终架构边界

Task09 完成后，QRP v1.1 的每日产品结构应是：

```text
Formal Pipeline Contracts
        ↓
Production Job Instances
        ↓
Existing QRP Job Runtime
        ↓
System B facts / ranks
        ↓
Formal System B Strategy
        ↓
Complete Portfolio Target
        ↓
Daily Closeout
```

新增能力时的增长方式必须保持：

```text
新增业务能力
→ formalize/register capability
→ workflow 通过 Contract dependency 引用
```

而不是：

```text
新增业务能力
→ 修改一个越来越大的 daily pipeline 函数
→ 手工继续堆调用顺序和错误处理
```

> **Task09 最终设计原则**：业务逻辑留在业务模块，依赖留在 Contract，部署留在 Production Job，运行状态留在 Job Runtime；Daily Product 只负责把这些既有能力正式闭环，不再复制它们。
